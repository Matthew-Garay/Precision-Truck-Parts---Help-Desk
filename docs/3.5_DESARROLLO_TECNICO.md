# 3.5 Desarrollo Técnico del Sistema

---

## 3.5.1 Estructura del Proyecto y Control de Versiones

El proyecto se organizó bajo un monorepo de directorio único llamado `PrecisionTrucks_HelpDesk/`, donde conviven el frontend y el backend dentro de la carpeta `src/`. Esta decisión permitió compartir configuraciones, ejecutar ambos procesos en paralelo con un solo comando (`npm run dev:all`) y simplificar el despliegue en producción, donde Express sirve directamente el build estático generado por Vite.

Dentro de `src/Backend/` se separaron las responsabilidades en capas bien definidas: `Config/` para conexiones y servicios externos, `Controllers/` para la lógica de negocio, `Middlewares/` para validación y seguridad, `Models/` para las consultas a la base de datos, `Routes/` para el enrutamiento HTTP y `Workers/` para los procesos en segundo plano. El frontend en `src/Frontend/` siguió la misma lógica con `Components/`, `Config/`, `Pages/` y `Styles/`.

Para el control de versiones se utilizó Git con un archivo `.gitignore` que excluye explícitamente el archivo `.env`, el contenido de `storage/` y el archivo `Workers/alert_state.json`. Esto garantiza que ningún secreto ni archivo binario de usuario quede registrado en el historial del repositorio.

## 3.5.2 Capa de Persistencia y Configuración de Conexiones

La base de datos elegida fue MySQL 8 con motor InnoDB y juego de caracteres `utf8mb4_unicode_ci`, lo que garantiza soporte completo para caracteres especiales del español. El esquema se compone de once tablas relacionadas: catálogos (`departamento`, `rol`, `sucursal`, `categoria`), entidades principales (`empleado`, `ticket`, `insumo`, `solicitud`, `manual`) y tablas de unión o historial (`solicitud_insumo`, `historial_acceso`).

La conexión al motor de base de datos se gestiona mediante un pool de conexiones configurado en `src/Backend/Config/db.js` usando la librería `mysql2/promise`. El pool permite hasta diez conexiones simultáneas con una cola máxima de cincuenta peticiones en espera, lo que evita la apertura de una conexión nueva por cada solicitud HTTP y mejora el rendimiento bajo carga concurrente. La zona horaria del pool se fijó en `-06:00` (Hermosillo, México) para que todas las marcas de tiempo almacenadas y leídas sean consistentes con el horario local de operación. Al iniciar el módulo se realiza una conexión de prueba; si falla, el proceso termina con código de salida 1 para impedir que el servidor arranque sin base de datos disponible.

Los folios de tickets (`PTP-YYYYMM-NNN`) y solicitudes (`SOL-YYYYMM-NNN`) se generan dentro de una transacción con bloqueo `SELECT ... FOR UPDATE` sobre la última fila del mes, lo que previene duplicados incluso bajo alta concurrencia.

## 3.5.3 Desarrollo del Backend (API RESTful y Seguridad)

El servidor backend se construyó con Node.js y Express 5, cuyo punto de entrada es `src/Backend/server.js`. Al arrancar, el proceso valida que las cinco variables de entorno críticas (`JWT_SECRET`, `DB_HOST`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`) estén definidas; si alguna falta, el proceso termina de inmediato. A continuación se configura el servidor HTTP nativo sobre el que se monta tanto Express como Socket.io, evitando la necesidad de dos puertos distintos.

La API expone más de cuarenta endpoints agrupados en cinco prefijos: `/api/auth`, `/api/tickets`, `/api/solicitudes`, `/api/categorias` y `/api/manuales`. Todos los endpoints de mutación (POST, PUT, PATCH, DELETE) pasan por tres capas de protección antes de llegar al controlador: autenticación JWT mediante el middleware `requireAuth`, protección CSRF basada en el header personalizado `x-requested-with` implementada en `security.js`, y validación de esquema con Zod 4 en `validate.js`. Las rutas de administrador añaden una cuarta capa con `requireAdmin`, que verifica que el rol del token sea 1.

La seguridad se complementó con Helmet para establecer cabeceras HTTP defensivas (CSP, HSTS, X-Content-Type-Options), rate limiting diferenciado por endpoint (10 intentos de login por 15 minutos, 30 tickets por hora por IP), y la función `safeResolvePath()` que neutraliza ataques de path traversal en todas las operaciones de archivo al normalizar y verificar que la ruta resuelta quede dentro del directorio base permitido.

## 3.5.4 Desarrollo del Frontend (Single Page Application y Responsividad)

El frontend se desarrolló como una Single Page Application (SPA) con React 18 y Vite 6 como bundler. El enrutamiento se maneja con React Router DOM 7, que protege las rutas privadas verificando la presencia del JWT en `localStorage` antes de renderizar cualquier página. Existen dos shells de dashboard independientes: uno para el rol Administrador (`src/Frontend/Pages/Admin/Dashboard.jsx`) y otro para el rol Usuario (`src/Frontend/Pages/Usuario/Dashboard.jsx`), cada uno con su propio sidebar y conjunto de páginas accesibles según los permisos del rol.

El sistema de estilos se construyó con Tailwind CSS 4 integrado directamente como plugin de Vite, complementado con un sistema de diseño propio definido en `DesignSystem.js` y `themeTokens.js` que centraliza los tokens de color para los modos claro y oscuro. El cambio de tema persiste en `localStorage` y se aplica globalmente mediante el `ThemeProvider` de `ThemeContext.jsx`.

La comunicación con el backend se centraliza en `api.js`, que expone la función `apiFetch()`. Esta función adjunta automáticamente el JWT, agrega el header CSRF en mutaciones, serializa el body a JSON cuando corresponde y redirige al login si el servidor responde con un 401. Todas las rutas de la API se definen como constantes en el objeto `API_ROUTES` para evitar URLs dispersas en el código.

## 3.5.5 Integración de Servicios Asíncronos y Tiempo Real

La comunicación en tiempo real se implementó con Socket.io 4, montado sobre el mismo servidor HTTP que Express para compartir el puerto 3001. Al establecer la conexión, el cliente envía el JWT en el campo `auth.token` del handshake; el servidor lo verifica y une el socket a dos salas: `empleado_{id}` (personal de cada usuario) y `admins` (compartida por todos los administradores). Esto permite enviar notificaciones dirigidas sin necesidad de mantener un mapa manual de sockets activos.

El servidor emite once tipos de eventos distintos: cinco dirigidos a usuarios individuales (cambio de estatus de ticket, técnico asignado, solicitud actualizada, confirmación de creación y cancelación) y seis dirigidos a la sala de administradores (nuevo ticket, nueva solicitud, ticket calificado, tickets vencidos por SLA, advertencia de SLA próximo, stock crítico y ticket sin atender). En el frontend, el hook `useSocket` suscribe al componente a todos estos eventos y los despacha a un callback unificado, manteniendo la referencia del callback actualizada mediante un `useRef` para evitar recrear la conexión WebSocket cuando cambia el estado del componente.

Los cinco workers en segundo plano se inician al arrancar el servidor desde `scheduledJobs.js` y reciben la instancia de Socket.io para poder emitir eventos. Cada worker usa un guard de solapamiento que impide que una ejecución lenta se superponga con la siguiente invocación del intervalo. Los Sets de deduplicación que evitan reenviar la misma alerta persisten en disco en `alert_state.json`, sobreviviendo reinicios del servidor.

## 3.5.6 Integración con Servicios Externos / APIs de Terceros

El único servicio externo integrado es el envío de correos electrónicos mediante Nodemailer 9, configurado en `src/Backend/Config/mailer.js`. El transporter se conecta a un servidor SMTP externo (configurado para Gmail con contraseña de aplicación, aunque es compatible con cualquier proveedor SMTP) usando las variables de entorno `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER` y `SMTP_PASS`. Si `SMTP_USER` no está definido, las funciones de envío retornan silenciosamente sin lanzar error, lo que permite ejecutar el sistema en entornos de desarrollo sin configuración de correo.

Se implementaron dos plantillas de correo HTML responsivas con soporte para modo oscuro mediante media queries CSS: una para el envío del código de recuperación de contraseña de seis dígitos (válido por diez minutos) y otra para la notificación de creación de ticket. Ambas plantillas incluyen el logotipo de la empresa como adjunto inline (`cid:logoptp`) para que se muestre correctamente en clientes de correo que bloquean imágenes externas. La fecha y hora en los correos se formatea en zona horaria `America/Hermosillo` usando la API nativa `Intl.DateTimeFormat`.

## 3.5.7 Gestión de Archivos y Almacenamiento

El almacenamiento de archivos se resolvió de forma local mediante el sistema de archivos del servidor, organizado en la carpeta `storage/` con cuatro subdirectorios según el tipo de contenido: `Evidencias_Tickets/` para imágenes y videos adjuntos a tickets (organizados por folio del ticket), `Fotos de Perfil/` para avatares de empleados, `Insumos/` para fotografías del inventario y `Manuales/` para los PDFs del módulo de documentación.

La subida de archivos se gestiona con Multer 2, con tres middlewares especializados según el tipo de contenido. El middleware `uploadEvidencias.js` acepta imágenes (JPEG, PNG, WebP, GIF) y videos (MP4, WebM, MOV, AVI) con un límite de 100 MB por archivo. La validación opera en dos capas independientes: primero Multer filtra por el MIME type declarado por el cliente en el header `Content-Type`, y después un middleware secundario lee los bytes mágicos del archivo ya guardado en disco usando la librería `file-type` para verificar que el contenido real coincida con el tipo declarado, impidiendo que un archivo malicioso renombrado con extensión `.jpg` evada el filtro. Las imágenes de evidencia pasan adicionalmente por `sharp` para ser redimensionadas a un máximo de 1920×1920 píxeles y recomprimidas a JPEG con calidad 75, reduciendo el espacio en disco sin pérdida perceptible de calidad.

El acceso a los archivos se controla a nivel de servidor: la ruta `/storage` bloquea el acceso a archivos `.json` y `.env`, mientras que la ruta `/fotos` requiere un JWT válido antes de servir cualquier imagen de perfil. La función `safeResolvePath()` se aplica en todas las operaciones de lectura y escritura de archivos para prevenir ataques de path traversal.

## 3.5.8 Caché y Optimización de Rendimiento

La optimización del rendimiento se abordó en múltiples niveles del stack. En el servidor, todas las respuestas HTTP pasan por el middleware `compression` (gzip/deflate), que reduce significativamente el tamaño de las respuestas JSON y de los archivos estáticos transferidos al cliente. Las rutas de autenticación incluyen el header `Cache-Control: no-store` para impedir que navegadores o proxies intermedios almacenen respuestas que contienen tokens o datos sensibles.

En la capa de base de datos, el pool de conexiones de `mysql2` evita el costo de establecer una nueva conexión TCP por cada petición HTTP. Las tablas con mayor volumen de consultas cuentan con índices compuestos definidos en el esquema: `idx_solicitud_estatus_fecha` en la tabla `solicitud` para acelerar los filtros por estatus y rango de fechas, e `idx_manual_categoria` en la tabla `manual`. Las consultas de generación de folios usan `SELECT ... FOR UPDATE` dentro de una transacción para garantizar consistencia sin recurrir a bloqueos de tabla completos.

En el frontend, el hook `useAutoRefresh` pausa el polling de datos cuando la pestaña del navegador no está visible (evento `visibilitychange`), eliminando peticiones HTTP innecesarias cuando el usuario no está interactuando con la aplicación. Al volver a la pestaña, si transcurrió más tiempo del intervalo configurado, ejecuta una recarga inmediata para que los datos estén frescos. Vite 6 genera el build de producción con code splitting automático, separando las dependencias de terceros en chunks independientes que el navegador puede cachear entre versiones. La dependencia `pdfjs-dist` se pre-optimiza explícitamente en `vite.config.js` mediante `optimizeDeps.include` para que su worker de Web Worker quede preparado desde el primer arranque del servidor de desarrollo.
